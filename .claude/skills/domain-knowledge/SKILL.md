# ドメイン知識 skill の生成

## 概要
ユーザーが選んだ参照元（設計書・コード・両方）から下書きを作り、参照元から分からない点だけをユーザーに**1問ずつ**質問して、業務領域ごとの skill を生成・更新する。
生成物の読み手は Claude。ただし業務ルール・業務フローは、マネジメント層の担当者も読んで確認できる業務の言葉で書く。確定した事実だけを本文に書き、推測は本文に書かない。

---

## 起動のしかた
| 起動のきっかけ | 最初の動き |
| --- | --- |
| ユーザーが作成・更新を依頼した | 手順0から始める |
| 別の作業中に、業務知識が足りないと分かった（用語・ルールの意味が分からず、該当する domain-* skill が無い） | 元の作業を止めずに、「〈用語・ルール〉の意味が分かりません。ドメイン知識の skill を作成しますか？」を1問で確認する |
| 別の作業中に、domain-* skill とコードの食い違いに気づいた | 元の作業を止めずに、「〈skill名〉の〈項目〉がコードと食い違っています。更新しますか？」を1問で確認する |

確認で「はい」なら元の作業を区切りのよいところで止めて手順0から始め、終わったら元の作業に戻る。「いいえ」なら元の作業を続け、同じ会話の中では同じ提案をしない。

---

## 生成物
対象プロジェクトに以下を作る。

```
.claude/skills/
  domain-<領域名>/        # 業務領域ごとに1つ（例: domain-order）
    SKILL.md              # 概要と、他のファイルを読む場面の指示
    glossary.md           # 用語集
    rules.md              # 業務ルール
    flows.md              # 業務フロー
    entities.md           # エンティティと関係（補助）
  domain-common/          # 複数領域にまたがる用語・ルール（構成は同上）
.claude/domain-knowledge/
  open-questions.md       # 未確認事項（回答が得られなかった質問・打ち切りで聞かなかった質問）
```

- 書く項目が1つも無いファイルは作らず、その領域の `SKILL.md` の表からも外す（`SKILL.md` と `glossary.md` は必ず作る）。
- 複数の領域で使われる用語（ファイルの置き場所ではなく、実際に参照している領域が複数あるもの）は `domain-common` にだけ書き、各領域からは「`domain-common` を参照」と書く。
- ルールは、その結果が影響する領域に書く（例: 会員ランクによる割引は受注、GOLD の引当特例は在庫）。複数領域の結果に影響するルールだけを `domain-common` に書く。
- 読むのは手順0で選ばれた参照元だけ。コードはアプリケーションコードのみ（DB定義・テスト・git履歴は読まない）。設計書は指定されたパスの Markdown・テキスト（`.md`・`.txt`）のみ。

---

## 手順
上から順に行う。各ステップの確認を省略して次へ進んではいけない。

0. **参照元の選択**: 実行のたびに、参照元を「A. 設計書 / B. コード / C. 両方」から1問で選ばせる。A か C なら、続けて設計書のパス（ファイルまたはディレクトリ）を1問で聞く。指定先に `.md`・`.txt` が無ければ「対応形式は Markdown・テキストのみ」と伝え、変換後のパスを聞き直す。
1. **領域の提案**: 参照元（設計書の章立て、コードのディレクトリ・モジュール・型名）から業務領域の分け方と `domain-common` に入る候補を提案し、1問で確定させる。引数で領域が指定されていればその領域だけを対象にし、この確認は省略する。
2. **既存 skill の確認**: 対象領域の `domain-*` が既にあれば、手順 3〜6 を「差分更新」として行う（後述）。
3. **下書き**: 参照元から用語・ルール・フローを抽出する。「両方」の場合は設計書とコードを項目ごとに突き合わせ、次を「矛盾」の質問にする。
   - 設計書とコードで内容が食い違う項目
   - 設計書にだけ書かれ、コードに実装が無い項目（人の作業・別システムの処理も含む。1項目1問）
   コードにだけある項目はそのまま書く。この時点ではファイルに書かない。
4. **質問**: 「質問のルール」に従い1問ずつ質問し、回答を下書きに反映する。
5. **確認**: 書き出す内容の要約（領域ごとの用語数・ルール数・フロー数と、今回の回答で確定した項目の一覧。数は ID・表の行の数で、参照だけの行は数えない）を示し、書き出してよいかを1問で確認する。
6. **書き出し**: `templates.md` を読み、その書式に従ってファイルを書く。手順5で確認した内容から項目を増減・変更する必要が出たら、書き出す前に変更点だけを示して再確認する。
7. **未確認事項**: 「未確認事項（open-questions.md）」に従って `open-questions.md` を書き、最後に状態ごとの件数とパスを報告する。

## 質問のルール

### 質問する場面（この4つだけ）
| 種類 | 例 |
| --- | --- |
| 矛盾 | 2か所でキャンセル可能な状態の判定が異なる。設計書とコードの食い違い、設計書にだけある記述、バグに見える挙動も含む |
| フローの欠落 | 承認フラグを更新する処理・記述が参照元に無い（人手・別システム） |
| ルールの理由（業務上の基準値のみ） | なぜ 72 時間でタイムアウトするのか |
| 意味不明な用語 | `kbn`、`flg2`、`status = 3` の業務上の意味 |

「ルールの理由」を聞くのは、変更に業務側の判断が要る**業務上の基準値**だけ。金額・期間・数量・時刻の閾値（例: 承認が必要になる金額、支払期限、バッチの実行時刻）と、特定の顧客・条件を優遇または制限する分岐（例: GOLD 会員だけ安全在庫まで引き当てる）が該当する。割引率・表示件数などの単純な設定値と、顧客ごとの与信枠のようなマスタに登録される値の理由は聞かない。理由がコードのコメントや設計書に書かれていれば聞かない。

推測で補える程度の不明点（例: `isCorporate` がある `kbn === "2"` は法人）は質問せず、参照元から読める範囲だけを書く。

### 質問の形式
- **1回のメッセージに質問は1つだけ**。答えを受け取ってから次の質問をする。返答を求めない報告（手順7など）には質問を含めない。
- **1問に論点は1つだけ**。互いに依存する論点（例: 顧客区分の値の有無と、その区分の自動キャンセル対象）は、前提になる方を先に聞き、その回答を踏まえて次を聞く。
- 回答で決まったルールと食い違う実装が別の箇所に残っていれば、回答をその箇所にも当てはめず、新しい「矛盾」として質問する。
- 上の表の順（矛盾 → フローの欠落 → ルールの理由 → 用語）に聞く。前の回答で不要になった質問は捨てる。
- 種類の区切り（矛盾 → フローの欠落、フローの欠落 → ルールの理由、ルールの理由 → 用語）ごとに、残りの種類ごとの件数（例: フローの欠落 4件、ルールの理由 4件、用語 0件）を示して「続けますか？」を1問で確認する。次の種類が0件なら確認せず、その次の区切りへ進む。
  - 「続けない」なら、その種類以降の質問はすべて聞かずに未確認事項（状態は `未質問`）として記録し、手順5へ進む。
  - 矛盾は区切りの確認の対象外で、必ずすべて聞く。「続けない」の後に回答や見直しで新しい矛盾が生じた場合も聞く。
- 回答や下書きの見直しで新しい質問が生じたら、まだ聞いていない質問に加えて上の順に並べ直す（矛盾なら次に聞く）。
- 可能な限り選択肢で答えられる形にし、最後に「その他」「分からない」を含める。選択肢は参照元の記述・実装から考えられるものに限る。
- 各質問には、根拠となる場所（コードのファイルと関数、設計書のファイルと見出し）と「回答によって何が決まるか」を1行で添える。

```
Q3. 〈質問文〉
根拠: `src/order/orderService.ts` の cancelOrder と `src/order/cancelOrderController.ts` の判定
決まること: rules.md のキャンセル可否ルール

- A. 〈選択肢〉
- B. 〈選択肢〉
- C. 分からない
```

### 回答が得られない場合
「分からない」「担当者に確認しないと不明」と答えられた質問は、本文に**何も書かず**未確認事項（状態は `回答不明`）として記録する。
矛盾の片方だけ・推測の意味だけを本文に書くこともしない。
前提の質問が「分からない」なら、それに依存する質問は聞かず、「未確認事項（open-questions.md）」に従って前提の質問とあわせて記録する。
値の一覧（コード値・区分など）の一部だけが食い違って未回答の場合は、一致した値も含めて一覧全体を本文に書かない（一部だけ書くと、それで全てだと読まれるため）。
ルールの適用範囲の一部だけが未回答の場合（例: 画面からのキャンセルは確定、自動キャンセルへの適用は未回答）は、確定した範囲を「内容」列に明記して書く。
ただし、参照元で確定している部分は書く。例: ルールの内容は参照元から確定し、理由だけが「分からない」なら、ルールを書いて「理由」列を空欄にし、理由の質問だけを未確認事項として記録する。

## 記述のルール
本文（`glossary.md`・`rules.md`・`flows.md`・`entities.md`）には、参照元から読み取った事実と回答で確定した事実だけを書く。出典・確度などのラベル（`〔コード〕` `[推測]` `[未確認]` など）は付けない。

### rules.md・flows.md は業務の言葉で書く
参照元にコードを含む場合も、`rules.md`・`flows.md` は設計書・業務マニュアルと同じ書き方にする。業務の担当者やマネジメント層がそのまま読んで、ルールとして正しいかを確認できる内容にする。
- コード上の名前（クラス・関数・変数・フラグ名）、ファイルパス、コード値（`9`、`"2"` など）を書かない。
- 技術用語（リポジトリ、バッチのジョブ名、例外、API、テーブル など）を使わず、業務上の呼び名で書く。
- 用語は `glossary.md` の「用語」列の名前を使う。コード上の名前との対応は `glossary.md` にだけ書く。
- 処理の仕組みではなく、業務上の結果として書く（例: ×「cancelOrder が release を呼び allocated を減らす」→ ○「受注をキャンセルすると、引き当てていた在庫を解除する」）。

## 未確認事項（open-questions.md）
本文に書けなかった質問を `.claude/domain-knowledge/open-questions.md` に記録し、人が後で確認できるようにする。

### 記録する質問
| 状態 | 記録する場面 |
| --- | --- |
| `回答不明` | 質問したが、「回答が得られない場合」に該当した |
| `未質問` | 種類の区切りの確認で「続けない」と答えられ、聞かなかった |

前提の質問が `回答不明` で聞かなかった依存する質問は、別の行にせず、前提の質問の行に「あわせて確認: 〈依存する質問〉」として書く。

### 書き出し（手順7）
- 書式は `templates.md` の open-questions.md に従う。
- ファイルが既にあれば、今回対象の領域の節だけを置き換え、それ以外の領域の節はそのまま残す。
- 全領域で質問が0件になる場合はファイルを作らない。既にあれば削除し、手順7の報告で「未確認事項は0件」と伝える。

### 差分更新での扱い
対象領域の節に残っている質問を、次のように扱う。対象外の領域の節は読まず、変更もしない。
1. `回答不明` の質問が1件以上あれば、差分更新の質問（差分更新の2.）より前に、その一覧を示して「このうち回答が分かったものはありますか？」を1問で確認する。分かったと答えられた質問は、今回の質問に含める。
2. 1.で分かったと答えられなかった `回答不明` の質問は、その「背景」に書いた箇所の内容が変わっていれば再度質問する。同じ関数内でも該当箇所が変わっていなければ再質問しない。
3. `未質問` の質問は今回の質問に含める。
4. 回答が得られた質問は一覧から消す。今回も回答が得られなかった質問・聞かなかった質問は、その時点の状態で残す。

## 差分更新（既存 skill がある場合）
1. 既存の内容と参照元を突き合わせ、候補を「追加 / 変更 / 削除」に分けて一覧で提示する（一覧は最初の質問と同じメッセージに載せてよい）。
2. 次の順に1問ずつ質問する。
   1. 既存の項目と参照元の食い違い（「矛盾」として質問する。既存の項目は過去の回答で確定した可能性があるため、自動で変更・削除しない）
   2. 候補の採否（変更・削除は1件ずつ。追加は一覧でまとめて1問で確認してよい）
   3. 採用した候補について生じた、フローの欠落・ルールの理由・用語の質問
3. 回答や採否から自動的に決まる他ファイルの修正（例: rules.md の期間変更に伴う flows.md の同じ数値）は個別に質問せず、手順5の要約に含めて確認する。
4. 未確認事項は「未確認事項（open-questions.md）」の「差分更新での扱い」に従う。
5. ID は既存のものを変えず、追加は各ファイルの最大番号の次を使う。削除した ID は再利用しない。

## 書式
生成するファイルの書式は `templates.md` にまとめている。書き出すとき（手順6・7）に読む。

## よくある誤り
| 誤り | 正しい動き |
| --- | --- |
| 質問を3〜4問まとめて出す | 1メッセージ1問。回答を待ってから次へ |
| 領域の分け方を確認せず、全領域を1つの skill にまとめる | 手順1で提案し、確定させてから進む |
| `[推測]` `[未確認]` などのラベルを付けて本文に書く | 本文は確定した事実のみ、ラベルなしで書く。不明点は open-questions.md へ |
| rules.md・flows.md に関数名・フラグ名・コード値を書く | 業務の言葉で、業務上の結果として書く。コード上の名前は glossary.md にだけ書く |
| 矛盾・バグの疑いを「現状の挙動」として本文に書く | 矛盾として質問する。回答が無ければ本文に書かない |
| 領域を指定した実行で open-questions.md を今回の質問だけで書き直す | 今回対象の領域の節だけを置き換え、他の領域の節は残す |
| 再実行時に全体を作り直す | 差分更新の手順に従い、既存の項目は質問せずに変更・削除しない |
| 参照元を聞かずに、見つけた設計書やコードを読み始める | 手順0で参照元を選ばせてから読む（ファイル名の一覧を見るのは可） |
| 選ばれた参照元以外（README・テスト・DB定義、指定外の設計書）を読んで下書きする | 選ばれた参照元だけを読む |
| 「両方」で設計書とコードが食い違うとき、どちらかを正として書く | 矛盾として質問する |
| 「両方」で設計書にだけある記述（バッチ・承認者など）を確定として書く | 1項目ずつ矛盾として質問する |
